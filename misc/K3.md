# Kimi K3 SafeTensors and GGUF inference plan

Branch: `kimi-k3`.

This document is the implementation and measurement plan for running the
official `moonshotai/Kimi-K3` checkpoint from either its SafeTensors shards or
the mixed-precision GGUF described below. The text runtime targets Apple
Metal. The direct path preserves the checkpoint's native MXFP4 expert weights
and uses block-scaled 8-bit activations for expert matrix multiplications.

The mandatory starting point is layer-major execution for both prefill and
generation:

1. Execute layer `L`.
2. While the GPU executes `L`, issue storage reads for layer `L + 1`.
3. Do not introduce a different execution order until this design has been
   instrumented, tuned, and shown to be at its real floor.

The current branch has the direct SafeTensors parser, K3 tensor binding, Metal
kernels, tokenizer, layer-major runtime, asynchronous next-layer loading, and
real-checkpoint tests. The pinned checkpoint is complete locally: 96 shards,
about 1.56 TB, revision
`2496450e92e425c886db095102a52a6682ca3970`.

## 0. Implemented baseline and measured floor

This section records what was actually built and measured on an Apple M5 Max
with 128 GiB unified memory. The rest of this document retains the original
plan and the gates for future work.

### 0.1 Existing SSD-streaming patterns reused

The implementation was based on the repository's established Metal paths, in
particular:

- `metal_graph_prefill_layer_major`, which joins the current layer prepare,
  starts future layer preparation, maps exact spans, executes one layer command
  buffer, and releases ownership at the layer boundary;
- `metal_graph_eval_token_raw_swa_streaming`, which maps only the current
  decode layer, starts readahead for the next layer, and prefetches the output
  head at the tail;
- the GLM selected-expert stream, which uses fixed Metal-visible buffers,
  explicit parallel `pread`, and overlaps missing expert I/O with independent
  current-layer work.

K3 follows the same ownership rules. Its loader validates and addresses either
official SafeTensors spans or a GGUF v3 tensor directory through one tensor
descriptor interface.

### 0.2 Initial one-row generation schedule

One-row prefill and every decode step use two fixed static slots. Slot parity is
the layer parity:

```text
join static(L)
start uncached static(L + 1) read into the other slot
map the current slot as a Metal no-copy weight source
execute attention and router
read 16 selected experts into the first 16 fixed expert slots
execute routed/shared work and finish the layer command buffer
release all Metal model views
```

Static reads and selected-expert reads open dedicated read-only descriptors and
apply macOS `F_NOCACHE`. The SafeTensors parser/mmap descriptor is separate and
is never changed to uncached mode. This matters because ordinary `pread`
sweeps left about 113 GiB of inactive file-backed pages after several tokens,
in addition to the explicit staging buffers. With `F_NOCACHE`, a complete
125.4 GiB layer/expert pass increased file-backed residency by only about
2.4 GiB, which corresponds to the separately mapped output head.

The static slots are sized independently by parity. Layer 0 is the largest
static layer because of its dense MLP; only the even slot needs that maximum
capacity. When the even slot is reused for layer 2, pages above the smaller
next size are discarded with `MADV_DONTNEED`. The exact routed-expert bank has
64 reusable slots. Decode uses only its first 16 slots, while multi-row prefill
fills the bank in batches:

```text
64 * 17,547,264 = 1,123,024,896 bytes = 1.046 GiB
```

Thus overlap requires the current static layer, the next static layer, and one
bounded selected-expert bank, not the full checkpoint. This bank is allocated
before the resident-static budget is computed, so its full capacity is always
charged. The two static slots are required by the stated
current-layer/next-layer overlap; one slot alone would serialize load and
compute.

Every expert is physically contiguous in the checkpoint in this order:

```text
w1 payload, w1 scales, w2 payload, w2 scales, w3 payload, w3 scales
```

The loader validates this for all 896 experts in every routed layer. Each
selected expert therefore needs one contiguous read, not six reads. Routed
latent activations are dynamically quantized to MXFP8 once per decode layer and
reused by all 16 experts. Expert intermediate activations are quantized again
before the down projection.

### 0.3 Multi-row prefill schedule

Multi-row prefill remains layer-major but does not copy static weights into the
decode slots. It:

1. starts advisory readahead for the next layer's static range;
2. maps the current static range as exact Metal spans;
3. runs attention and routing;
4. streams each selected expert's one contiguous MXFP4 range through the
   64-slot bank, consuming large selections in bounded batches;
5. fences Metal only before reusing the bank for the next batch, so no
   per-prompt Metal allocation scales with the number of selected experts;
6. finishes the layer command buffer, releases Metal views, and unmaps the
   shard before advancing.

The previous fallback created 400-900 disjoint no-copy Metal buffers per layer
for a short rendered chat prompt. With resident static buffers already pinned,
Metal could reject that first routed-layer map. The bounded path was tested end
to end on a 41-token rendered prompt: it streamed 294.551 GiB of experts at
8.28 GiB/s, completed prefill in 68.447 seconds, held process RSS near 1.1 GiB
with static residency disabled, and did not create routed-expert model views.

### 0.4 SSD concurrency sweep

`K3_STATIC_IO_THREADS` was swept after uncached descriptors were enabled.
`K3_EXPERT_IO_THREADS` was swept independently and under static contention.
The selected defaults on this machine are 16 static readers and 8 expert
readers.

Representative one-token results:

| Static path | Static threads | Expert threads | Total | Static throughput | Expert throughput |

| mmap + CPU page-in diagnostic | n/a | 8 | no improvement | n/a | n/a |
| staged, cached `pread` | 1 | 8 | 11.28 s | 9.67 GiB/s | 11.19 GiB/s |

The cached 8.53-second number is not the honest recurring floor: it consumed a
model-sized filesystem cache and was unsafe as a default on 128 GiB. The
uncached 9.52-9.98-second result is the applicable direct-SSD result. Reader counts
above eight prioritize known next-static traffic; eight expert readers give
the best balance once routing makes those reads eligible.

The deterministic raw prompt `x` produces `_{1` over two generated tokens in
both the original advisory path and staged path. A default two-token staged run
completed statefully with the same output. All guarded runs stayed above the
watchdog threshold; representative uncached runs bottomed at 90-92% system
memory free.

### 0.5 Load-hiding conclusion

The measured decode traffic agrees with Section 4:

- static weights: 101.339 GiB/token;
- 16 selected experts in 92 routed layers: 24.056 GiB/token;
- output head: 2.188 GiB/token.

Selected-expert loading can mostly be hidden inside current-layer work when it
has a sufficiently large worker pool. Static loading cannot be fully hidden:
even at 13.32 GiB/s aggregate static-read throughput, the 101.339 GiB stream
takes 7.61 seconds summed across layer jobs. Sixteen readers reduce measured
layer-ready wait to 0.084 seconds, but they contend with expert I/O and stretch
the execution interval. The end-to-end floor is therefore the balanced
critical path, about 10 seconds/token on this machine, rather than either I/O
sum in isolation.

This was the real floor of the minimal-memory layer-major design. The resident
design below beats it without changing the layer order or model math.

### 0.6 Resident static redesign and measured floor

The first resident BF16 prototype allocated one anonymous slab per layer but
retained the streaming view lifecycle: every layer created a new Metal
`newBufferWithBytesNoCopy` wrapper and destroyed it after the command buffer.
At 101.3 GiB this took more than two minutes per token. A process sample showed
the main thread waiting for the router shared event while the Metal submission
thread repeatedly wired and unwired the current layer. A 64 GiB version also
allowed anonymous pages to be compressed and reduced expert SSD throughput to
1.33 GiB/s. Capacity was not the issue; GPU VM ownership was.

The corrected design creates each resident layer's no-copy Metal buffer once,
adds all resident buffers to one persistent `MTLResidencySet`, and leaves that
set on the command queue for the context lifetime. These pinned K3 views are
separate from ordinary model views, so mapping or releasing the embedding,
nonresident staging slots, and output tensors cannot destroy them. Selected
prefill experts use the fixed Metal tensor bank rather than shard-backed model
views. K3 weight lookup checks the pinned views first. Nonresident layers still
use the two-slot layer-major pipeline, so partial residency does not introduce
a second execution order.

The original default used Metal's `recommendedMaxWorkingSetSize` minus current
Metal tensor allocations and only a 256 MiB reserve. That could overcommit a
busy Mac because the Metal recommendation does not account for other
processes. The integrated runtime caps this against immediately free plus
file-backed macOS pages, counting speculative pages only once and excluding
inactive anonymous pages that would require compression or swap. It retains
1/8 of physical RAM, clamped to 12-16 GiB. The two decode staging slots are
charged before resident layers are selected, and reclaimable memory is checked
again before every layer promotion; an unsafe plan is shortened before the
remaining mappings are faulted in. Explicit
`K3_RESIDENT_STATIC_GIB=N` requests are capped too unless
`K3_UNSAFE_RESIDENT_STATIC=1` is deliberately enabled for a controlled test.
`K3_MEMORY_RESERVE_GIB=N` adjusts the reserve and
`K3_RESIDENT_STATIC=0` disables residency. Selected-expert descriptors are
opened once per layer and retained across tokens.

Residency is allocated in this order:

1. the output head, whose otherwise exposed tail costs about 0.18 seconds;
2. complete static layers, which remove both SSD bytes and a layer-ready
   dependency;
3. shared-expert-only spans when the remaining budget cannot fit another
   complete layer.

The two shared experts are 264,241,152 bytes per routed layer, or about
22.63 GiB for all 92 routed layers. A 32 GiB shared-first experiment kept all
shared experts plus nine complete layers and measured 8.489 seconds. Complete
layers first, then two shared-only leftovers, measured 8.215 seconds at nearly
the same resident bytes. The shared-first policy is retained only as
`K3_RESIDENT_SHARED_FIRST=1`; full residency naturally keeps every shared
expert resident.

Those rows are the historical static-residency sweep before output-head
residency, embedding-row staging, and speculative expert prefetch. The final

An experimental runtime Q8_0 static cache was also implemented. It builds
53.51 GiB of Metal-owned Q8 weights directly from the BF16 SafeTensors in
16-19 seconds and uses the repository's optimized Q8 decode and prefill
kernels. Without a residency set it took 20.47 seconds/token; with residency
it took 8.33 seconds/token. The tensor-matrix decode variant was no faster and
changed the deterministic first token, so it was rejected. Q8 remains an
explicit `K3_Q8_STATIC=1` experiment rather than the quality or speed default.

Adjacent one-token routes overlapped by only 232 of 1,472 selected
layer-experts (15.8%). Retaining a complete previous route would consume
24.06 GiB to save about 3.8 GiB/token on that sample, which is less effective
than assigning the same memory to exact static layers. A routed cache remains
useful for workloads that demonstrate materially higher locality, but it is
not ahead of static residency in the current priority order.

### 0.7 Final M5 decode path

Full static residency leaves selected MXFP4 experts as the recurring storage
dependency. The exact control reads 24.056 GiB/token. It measured 3.123 seconds
before the persistent pool and embedding-row fix, and 2.665 seconds in the final
full-resident A/B. Applying the next layer's router directly to the current
`ffn_in` predicted only 58.2% of the next top-16. Reconstructing the next
layer's post-attention AttnRes mixture from the current prefix and saved blocks
raised recall to 70-72%. Predictions are skipped at AttnRes block boundaries,
where the unknown next attention output replaces the prefix.

Precision is strongly rank-dependent. Representative full-resident values
were:

| Predicted prefix | Precision |
|---:|---:|
| top-4 | 88.7-95.5% |
| top-8 | 87.1-88.2% |
| top-12 | 79.7-80.3% |
| top-16 | 70.4-72.0% |

Reading all 16 predictions reduced the first test only to 2.991 seconds
because wrong predictions increased expert traffic to about 30.25 GiB/token.
Top-8 is the measured optimum: it advances roughly seven true experts per
eligible layer while adding only about 1.4 GiB over the exact 24.056 GiB
traffic. Top-4 reduced wrong bytes further but measured 4.399 seconds at the
80 GiB comparison point versus 4.253 seconds for top-8.

Speculation never changes routing or model math. The true router is
authoritative; predicted slots are matched by expert ID and every miss is read
into the exact bank. A persistent eight-thread pool has separate exact-high and
speculative-low queues. When the exact route arrives, queued hits are promoted,
queued misses are canceled, and already-issued reads are allowed to retire.
This removes per-layer thread creation and starts the next predicted batch while
the current exact batch is still draining.

Speculative weights use two banks selected by target-layer parity. Raw-logit
fingerprints exposed two hidden correctness problems. First, ring depth alone
was timing-dependent because asynchronously flushed Metal command buffers could
still retain a bank when CPU refill began. The final path explicitly drains
pending GPU work before refill, opens a new command buffer, and then overlaps
the future read with the current layer's exact experts. Second, the predictor's
AttnRes pass used to round the live prefix in place. It now has a tested
read-only mode. With those explicit ownership rules, two banks are sufficient
and occupy 267.75 MiB.

Two other tail costs were removed:

- The 2.188 GiB BF16 output head is copied once and included in the persistent
  residency set. Output projection setup fell from about 0.18 seconds to
  0.006-0.008 seconds.
- Decode no longer creates a Metal model view over the full 2.188 GiB token
  embedding. It copies the requested 14 KiB BF16 row into a small shared tensor
  and expands it exactly on Metal. Non-layer evaluation overhead fell from
  roughly 0.43 seconds to about 0.01 seconds in the full-resident run.

Final guarded M5 Max measurements:

| Configuration | First evaluation | Steady decode | Minimum free |
|---|---:|---:|---:|
| full static + resident head, no speculation, old embedding view | 3.123 s | not measured | 10% |
| full static/head, persistent pool, no speculation | 2.697 s | 2.665 s | 12% |
| 80 GiB, resident head, no speculation | 4.27-4.67 s | 4.57 s representative | 30% |
| 80 GiB, persistent pool + top-8 speculation | 3.81-4.09 s | 4.08 s representative | 29-30% |
| automatic full static/head, fenced top-8 speculation | **2.226 s** | **2.075 s** | **11-16%** |

The final steady layer loop is 2.069 seconds while recurring expert traffic is
about 25.35 GiB: 14.365 GiB of exact misses and 10.982 GiB of predictions. At
the measured 10-12 GiB/s-class read rate this is close to the single-SSD
bandwidth floor. The persistent pool improved the earlier 2.106-second steady
result to 2.075 seconds; its main value is predictable priority and lifetime
management rather than a large change to the storage bound.

The exactness check hashes all 163,840 raw float logits. With identical resident
spans, control and speculation produced `3971413c29ca17a9` at position 1 and
`0538ec39c89df006` at position 2. Under full residency both paths produced
`9022f141aa829e65` and `65f56fb972042e7d`. This catches state differences that
matching greedy tokens would miss. `K3_LOGITS_FINGERPRINT=1` enables the
diagnostic.

Decode also uses two smaller GPU-side improvements. Router sigmoid scores are
evaluated across one SIMD group while lane 0 retains the reference insertion
and normalization order. Each one-row expert down projection applies its route
weight and accumulates directly into `routed_sum`, avoiding a temporary expert
output and scatter kernel. The old serial router remains available with
`K3_ROUTER_PARALLEL=0`.

Several plausible changes were measured and rejected as defaults:

- `K3_EXPERT_PIPELINE_BATCH=1` committed each expert early and improved some
  partial-residency timings, but changed deterministic output in the
  full-resident test.
- Runtime Q8 static residency halves BF16 storage but its decode kernels were
  slower and changed the deterministic token, so it remains experimental.
- Cross-token same-layer route overlap measured only 12.7-15.8%, far below the
  same-token next-layer predictor and not worth displacing exact static
  residency.
- Nine expert workers tied eight at the 80 GiB comparison point, while sixteen
  regressed the partial-resident path to 4.10 seconds. Eight remains the
  measured default.
- SafeTensors expert offsets are not page aligned, so an aligned `F_NOCACHE`
  prototype was tested on eight different cold shards. Native reads sustained
  12.81-13.05 GiB/s and aligned reads sustained 12.81-13.01 GiB/s. Alignment
  reduced system CPU time but did not improve storage latency, so the extra slot
  layout complexity was rejected.

### 0.8 Mixed Q2 GGUF and two-node residency

The resident deployment format keeps quality-sensitive non-routed weights at
their source precision and spends the Q2 budget only on the 896 routed experts
in layers 1 through 92:

| GGUF type | Tensors | Payload bytes | Payload GiB | Main tensor classes |
|---|---:|---:|---:|---|
| IQ2_XXS | 184 | 467,971,080,192 | 435.832 | Routed expert gate/up stacks |
| Q2_K | 92 | 297,799,778,304 | 277.348 | Routed expert down stacks |
| MXFP4 | 276 | 6,457,393,152 | 6.014 | Shared expert gate/up/down |
| Q8_0 | 94 | 3,025,928,192 | 2.818 | Stable LatentMoE up and layer-0 gate/up |
| BF16 | 1,584 | 83,459,000,320 | 77.727 | Embedding, head, attention and retained matrices |
| F32 | 506 | 44,489,728 | 0.041 | Router biases and scalar/state parameters |

The exact GGUF plan contains 2,736 tensors. Its payload is 858,757,669,888
bytes and the complete file, including metadata/alignment, is 858,760,729,248
bytes, or **799.783 GiB**. Vision tensors are omitted. The embedding and LM
head remain BF16. Shared experts remain standard GGUF MXFP4 as required.

Without an inference matrix, the converter uses a bounded activation-aware
proxy. One square-root-tempered, normalized input-importance vector is shared
by each layer's gate/up stacks. Each expert's down importance is derived from
the corresponding gate and up row energies, normalized per expert, with a
small floor and cap to prevent statistical outliers from consuming the whole
codebook. Conversion uses a fixed worker pool, one source layer at a time,
`F_NOCACHE`, a sparse `.partial` destination, and tensor-level progress
journaling. Resume requires the sparse file's exact planned size, a byte-exact
match of its complete deterministic GGUF header (including the tokenizer), and
a valid `K3QPRO1` journal. A persistent advisory lock excludes concurrent
writers, and a fresh conversion resets the journal before creating the sparse
header so stale progress cannot validate a new empty payload. Payload durable
sync (`F_FULLFSYNC` on Darwin) precedes every journal advance, finalization
rechecks the exact file size, and directory fsync makes journal and
final-output renames durable.

Two alternatives using the retained Stable LatentMoE down projection as a
proxy were tested against the same layer-20 SafeTensor reference. The
production expert-energy proxy gave relative RMSE `0.440648448` and cosine
similarity `0.904268574`. Square-root-tempered latent row energy gave
`0.441797154` and `0.903614800`; raw latent row energy gave `0.442533838` and
`0.903279046`. Both alternatives were worse, so the converter keeps the
expert-derived proxy and exposes no diagnostic proxy modes in its production
CLI.

The GGUF runtime uses the same layer-major schedule for prefill and generation.
In bounded mode it retains one canonical whole-file mapping, starts readahead
for the next layer's non-expert tensors, and uses parallel `pread` to copy only
the current router's selected IQ2_XXS gate/up and Q2_K down experts into
reusable Metal slabs. Address-table kernels consume those slabs directly, so
the GPU never faults through the multi-GiB complete routed stacks. One-token
gate/up projection, SiTU, route weighting, and Q2_K down summation are fused
for K3's top-16 route.

Batched prefill may select every expert in a layer. The bounded cache therefore
has a minimum capacity of 896 experts, up to 7.75 GiB for this recipe, and
reuses those same slabs for the next layer. A process owning all 92 routed
layers uses 1,472 slots, one top-16 set per layer, with a 12.74 GiB ceiling for
cross-token generation reuse. These are hard entry limits, not eager
allocations: slabs are created only as experts are encountered. A two-row
layer-3 regression selected 21 unique experts, read 0.18 GiB in 12.5 ms, and
matched the resident path's output checksum. On the same M5 Max, the immediate
bounded generation step took about 24 ms for the complete layer versus about
12 ms with that layer pinned resident. A cold standalone test also pays the
one-time Metal pipeline compilation cost; subsequent layers reuse the pipeline.

A 128-row, four-layer bounded stress test over layers 20 through 23 filled the
cache to exactly 896 entries (7.75 GiB), then handled 1,099 total misses by
evicting and reusing 203 slab slots. The replacement path used 15 batched
victim scans totaling 2.44 ms, performed no heap growth after the two backing
slabs were allocated, and completed the following generation step with the
deterministic checksum `3.952535846887e+03` and hash `9f76fa072ce1ad41`.
The test is reproducible with
`K3_TEST_LAYER=20 K3_TEST_STREAM_LAYERS=4 K3_TEST_PREFILL_ROWS=128
DS4_METAL_STREAMING_EXPERT_TIMING_SUMMARY=1 tests/test_k3_gguf_slice
MODEL.gguf`.
Reusable slab ownership is transferred explicitly into pending asynchronous
loads; every uninstalled slot is returned on preparation, read, or install
failure.

On a large-memory distributed node, it instead creates one persistent no-copy
Metal buffer per local layer from the globals shard's canonical GGUF mapping.
The buffers share one queue residency set and cover attention, routers, shared
experts, and complete routed stacks. The first pass still pipelines read-ahead;
subsequent generated tokens issue neither SSD advice nor per-layer Metal
buffer creation.

Resident GGUF layers are submitted continuously across layer boundaries.
Accumulator clearing is encoded as an ordered Metal blit, so the next layer
cannot race an in-flight routed reduction, and only the final local layer
drains the queue. Selected expert IDs remain GPU-resident, avoiding the router
readback required by the SSD-streaming paths. A two-layer resident generation
regression on the M5 Max verifies this cross-layer command schedule.

After the final router and MXFP4 matvec tuning, six repeated one-layer
evaluations on actual converted weights reached `2.537 ms` for KDA layer 1
and `1.809 ms` for MLA layer 3 after warmup. A two-KDA-layer pipelined test
averaged about `4.90 ms` per evaluation. These are local layer-path
measurements, not an end-to-end token result; layer 0, the output projection,
and distributed transport remain outside them.
Applying those actual-weight times to the 68 routed KDA and 24 routed MLA
layers gives about `0.216 s` for the routed transformer core. This suggests a
roughly 4-5 token/s two-node resident target after adding layer 0, the BF16
head, and FP32 boundary transport, but it remains a projection until the final
GGUF is measured end to end on the two 512 GiB machines.

Resident prefill uses a grouped IQ2_XXS gate/up matmul with an in-kernel
weighted SiTU epilogue and an F16 intermediate for Q2_K down. At 32 tokens,
the layer-1 routed stages changed from separate 8.1 ms gate, 8.1 ms up, and
6.4 ms activation passes to one 16.1 ms fused pass; the complete two-layer
first evaluation fell from 239 ms to 135 ms with the same checksum. The same
SiTU epilogue is enabled in the pair matvec used by 2-5 token resident suffix
prefills. One-token generation already uses its specialized fused pair kernel,
so this optimization intentionally does not change its measured floor.

Standard GGUF MXFP4 shared experts have both an MPP FP32-activation path and a
fused MXFP8-activation path. In the earlier resident layer-1 A/B on the M5 Max,
before the final router and matvec changes applied equally to both modes, the
complete layer averaged about 4.64 ms with MPP versus 5.18 ms with the A8
kernel, and FP32 also avoids another quantization error. MPP is therefore the
default; `K3_GGUF_SHARED_A8=1` retains the exact A8 experiment.
A fused FP32-activation gate/up+SiTU kernel was also measured and removed: it
raised steady two-layer decode from about 8.37 ms to 8.81 ms and changed the
accumulation order. Fewer launches did not compensate for the generic MXFP4
kernel's better tiling.

The next resident pass removed fixed overhead and corrected the short-suffix
path:

- the 2-5-token IQ2 pair kernel now receives SiTU's activation kind, beta, and
  linear beta rather than silently using its zero-initialized SwiGLU defaults;
- bounded and resident two-row layer-3 evaluation now match bit for bit at
  checksum `1.599027936035e+03` and FNV hash `28a4cea5217918a5`;
- resident GGUF layers no longer clear `routed_sum` before kernels that
  overwrite it, an already-idle synchronize no longer submits an empty command
  buffer, and the full-model embedding expansion stays in the first layer's
  command batch;
- the fused IQ2 gate/up+SiTU kernel no longer writes dead gate/up
  intermediates;
- top-16 prefill reduction uses one sum kernel rather than 15 dependent add
  dispatches. Its 32-token sum stage measured 0.20 ms, and the same profiled
  two-layer first evaluation measured 90 ms with hash-stable output.

The original scalar-path eight-step, two-layer resident decode regression
remained hash-stable at `7eee36a33ab515c5` and measured 8-10 ms per steady
step on the M5 Max. Forced stage boundaries gave the following scalar-path
one-layer breakdown:

| Stage | KDA layer | MLA layer |
|---|---:|---:|
| Attention and attention output | 2.50-2.58 ms | 1.55-1.63 ms |
| Post-attention AttnRes | 0.22-0.27 ms | 0.21-0.26 ms |
| Router, latent down, shared experts | 1.42-1.51 ms | 1.41-1.48 ms |
| Top-16 routed experts | 0.53-0.61 ms | 0.57-0.68 ms |
| Routed norm/up/add | 0.23-0.28 ms | 0.21-0.26 ms |

KDA attention reads roughly 0.9 GB of BF16 projection weights per layer, so
its measured interval is already primarily a unified-memory bandwidth cost.
The shared/static MoE block is now the largest common optimization target; a
custom fused MXFP4 gate/up kernel was nevertheless slower than the existing
generic path, as recorded above.

The BF16 decode projections now issue sixteen independent weight/input loads
before each same-order FMA sequence. This exposes memory-level parallelism
without changing the per-lane reduction order. Across 48 recurrent steps,
every tested scalar, four-load, eight-load, and sixteen-load configuration
produced the same raw output hashes. On resident layer 1 (KDA),
scalar/four/eight/sixteen-load averages were 4.30/3.54/3.48/3.46 ms; on
resident layer 3 (MLA), they were 3.32/2.89/2.86/2.85 ms. A two-KDA-layer
pipeline fell from 8.45 ms scalar to 6.87 ms with four-load and 6.75 ms with
eight-load unrolling. Combining KDA's four same-shape Q/K/V/gate projections
into one 3D dispatch reduced the eight-load result again to 6.71 ms.
Three alternating 128-step sixteen-load runs measured 6.694-6.704 ms for
separate dispatches and 6.684-6.686 ms for the fused dispatch, all with hash
`aaec5f7bfba07b7b`. Sixteen-load unrolling, four simdgroups, and fused QKVG
are the defaults. `K3_BF16_MV_UNROLL=0|4|8|16` and
`K3_BF16_MV_NSG=1|2|4|8` retain process-start tuning for other Apple GPUs.
`K3_DISABLE_FUSED_QKVG=1` provides the separate-dispatch control.
A contiguous `ushort4`/`float4` load layout was also tested. It changed the
lane reduction topology and recurrent hashes while regressing KDA to
3.53-3.55 ms and MLA to 2.88-2.89 ms, so it is not retained.

MLA now keeps each BF16 cache latent in a register between the score and value
updates instead of loading it twice. Its absorbed-query and value-up `kv_b`
loops also preload sixteen weights and activations before the same-order FMA
chain. The complete resident MLA layer fell from 2.84-2.86 ms to
2.756-2.761 ms over 128 recurrent steps, with the unchanged hash
`8d3e84fe83e0864d`. A 2,048-step resident layer-3 regression crossed the
1,024-token attention-partial boundary and completed with finite output,
checksum `3.776520231729e+05`, and hash `018e48550558cf0d`.

Router selection now computes each expert's exact rank in parallel. Rank is
the number of experts with a larger corrected sigmoid score, plus equal-score
experts with a smaller ID, so the first 16 ranks reproduce the reference
descending-score/ascending-ID insertion order exactly. Lane zero still
normalizes raw sigmoid weights in rank order. At 896 rank threads, the complete
resident KDA layer fell from 3.448-3.451 ms with parallel-score/serial-insertion
selection to 2.613 ms; MLA fell from 2.756-2.764 ms to 1.930 ms. Recurrent
hashes remained `86a1f87ec6d13b99` and `8d3e84fe83e0864d`. Rank also won at
32- and 128-token prefill with identical hashes. `K3_ROUTER_PARALLEL=score`
retains the old selector, `K3_ROUTER_PARALLEL=0` retains the fully serial
reference, and `K3_ROUTER_RANK_THREADS=128|256|512|896` supports per-GPU
tuning.

The next selector replaces all-pairs ranking with one 1,024-lane bitonic
network: 896 lanes hold experts and 128 hold negative-infinity sentinels.
Its compare order is still descending corrected score then ascending expert
ID, while lane zero retains the reference raw-sigmoid normalization order.
The same two-KDA-layer recurrent A/B fell from 5.026 ms with rank to 4.922 ms
with bitonic and retained hash `aaec5f7bfba07b7b`. One-layer 32-row prefill
averaged 40.776 ms versus 40.990 ms; 128-row prefill averaged 62.893 ms versus
63.492 ms, also with identical hashes. Bitonic is now the default;
`K3_ROUTER_PARALLEL=rank` retains all-pairs rank, and devices with fewer than
1,024 threads per threadgroup fall back to rank automatically.
Each bitonic record carries the already-computed raw sigmoid through the sort,
so lane zero no longer repeats 16 serial exponentials. Three final
two-KDA-layer averages were 4.910/4.899/4.899 ms with unchanged hash
`57ee00a00b6c9203`.

The order-preserving AttnRes split was retained as a small decode improvement:
parallel per-source score reductions preserve the original 256-thread tree,
then a separate mix/norm dispatch keeps source accumulation order. It saved
about 0.006-0.008 ms on KDA, was neutral on MLA and 32-token prefill, and
remained hash-identical. `K3_ATTN_RES_SPLIT=0` restores the monolithic kernel.

With all exact-order decode changes enabled, three 128-step two-KDA-layer
pipeline runs measured 5.004-5.006 ms, down from the 8.45 ms scalar baseline
and still at hash `aaec5f7bfba07b7b`.

Shared-expert gate/up now uses a pair wrapper around the same generic
`mul_mv_ext` MXFP4 implementation that won the earlier tiling comparison. It
loads FP32 input once, retains each matrix's exact dot-product reduction, and
applies SiTU at the output lane. This saved about 0.008 ms on KDA and
0.010-0.016 ms on MLA with unchanged hashes. A direct CPU-reference test
covers the fused GGUF MXFP4/FP32 result; `K3_DISABLE_GGUF_SHARED_PAIR=1`
restores separate generic gate/up dispatches. With the pair path included, the
steady 120 evaluations of a 128-step, two-KDA-layer resident regression
averaged 4.993 ms (4.934-5.092 ms) with the unchanged
`aaec5f7bfba07b7b` hash.

K3's 7,168-wide standard MXFP4 matvecs use 32 x-lanes per SIMD group by
default. A complete launch sweep measured about 2.560 ms per KDA layer at
32 lanes, 2.566-2.572 ms at 16, and 2.601-2.608 ms at 8. The 32-lane
reduction changes floating-point association, but its actual-weight comparison
was fractionally closer to the SafeTensor boundary: relative RMS error
0.100842381 versus 0.100842406 at 16 lanes. With bitonic routing and this
geometry, three 120-evaluation two-KDA-layer averages were
4.901/4.942/4.898 ms with deterministic hash `57ee00a00b6c9203`.
The corresponding MLA layer changed from 1.880 ms at 16 lanes to 1.872 ms at
32 lanes.
`DS4_METAL_MXFP4_MV_NXPSG=8|16|32` overrides this K3-only default.

Actual-weight boundary comparisons use identical two-step recurrent inputs and
the unquantized SafeTensor path as the reference. Layer 1 (KDA) measured
relative RMS error 0.100842381 and cosine similarity 0.994912585; layer 3
(MLA) measured 0.052946554 and 0.998598853. These checks exercise the emitted
tensor orientation and the complete shared-MXFP4, latent-Q8, routed-IQ2/Q2
runtime path. `K3_TEST_DUMP=FILE` and `K3_TEST_COMPARE=FILE` on
`tests/test_k3_gguf_slice` reproduce the binary boundary comparison.
At 32 prefill rows followed by one recurrent step, layer 1 measured relative
RMS error 0.062838915 and cosine 0.998024955; layer 3 measured 0.082772968 and
0.996568449. Those runs additionally cover grouped IQ2 gate/up+SiTU, selected
Q2 down reduction, and batch attention.
The documented coordinator's final layer, layer 46, was also compared after
its journal entry completed. Its one-step synthetic boundary measured relative
RMS error `0.442334820` and cosine similarity `0.902525650`, consistent with
the earlier deep routed-layer result. The worker's first layer, MLA layer 47,
measured `0.242822665` and `0.970462623` respectively. Together these exercise
both sides of the exact distributed split. A later two-step MLA check at layer
67 measured relative RMS error `0.149164344` and cosine similarity
`0.988844057`, with finite nonzero output on both prefill and generation.

A single 512 GiB machine cannot hold this file. The two-node resident design
therefore partitions contiguous layers rather than splitting every expert
matmul. The exact byte-balanced route is coordinator `0:46` at 401.163 GiB and
worker `47:output` at 398.617 GiB, assigning the embedding to the coordinator
and output tensors to the worker. Each node faults only its own layer range and
owns the KDA/MLA state for those layers. The boundary consists of K3's prefix,
current delta, and eight AttnRes blocks: 71,680 floats, or 280 KiB/token.
Both machines need `sudo sysctl iogpu.wired_limit_mb=480000` after boot. The
resulting ceiling is about 469 GiB, enough for either 399-401 GiB model slice
and its Metal state while leaving about 43 GiB outside the ceiling for macOS
and filesystem I/O.
K3 requires the FP32 distributed wire because the generic unscaled FP16/FP8
codecs cannot safely preserve this complete residual state. The output-owning
node executes the final AttnRes, norm, and LM head.
The worker HELLO advertises its real prefill capacity, and the coordinator
uses the minimum across the selected route. At 71,680 FP32 values per token,
the protocol's 32-bit frame length permits at most 14,979 K3 tokens per chunk;
the scheduler applies that limit before allocating or sending a chunk.
The full-resident read-ahead sweep is tracked on the shared execution owner:
the first evaluation warms every owned span, while resets, recovery replay,
and cloned sessions reuse the already-pinned mapping instead of repeating
hundreds of GiB of `F_RDADVISE` calls.
A guarded two-process loopback using the production `0:46` /
`47:output` route completed a 38-token prefill and a second full decode
traversal, returning both tokens through the coordinator. The test used the
in-progress sparse GGUF and bounded mode on one 128 GiB machine, so its output
and timing are control-path validation only. A second loopback advertised a
16-row worker capacity against a 64-row coordinator and completed the same
38-token prompt in negotiated chunks.

Full GGUF residency is automatic only on Macs with at least 256 GiB RAM and
only when the complete local span fits the same live-memory safety budget used
by the SafeTensors caches. `K3_GGUF_RESIDENT=0` disables it. An explicit
`K3_GGUF_RESIDENT=1` still cannot exceed the computed safe budget. This keeps
single-layer tests and the 128 GiB development machine on the bounded path.
Bounded GGUF never allocates or pins the separate SafeTensors static-layer
slots; its canonical GGUF mapping, selected-expert slabs, and optional resident
LM head are the only weight sources.
The GGUF static-span calculation explicitly includes layer 0's dense
gate/up/down tensors; the parser regression verifies that each complete tensor
range is covered before Metal mapping.

## 1. Scope and invariants

The production target is exact autoregressive inference behind DwarfStar's
common engine and session APIs:

- Read the official SafeTensors files directly, and support the mixed Q2 GGUF
  as an optional resident deployment format.
- Support prefill and generation with the same layer-major model traversal.
- Preserve the official model architecture and routing behavior.
- Keep expert weights in native MXFP4: E2M1 payload values plus E8M0 block
  scales, with a block size of 32.
- Quantize expert inputs and intermediate activations to MXFP8 dynamically.
  Attention, routing, shared experts, latent projections, normalization, and
  the output head continue to use their checkpoint dtypes or the precision
  required by the reference implementation.
- Never change selected experts, routing scores, or sampling to improve speed.
- Keep KDA recurrent state and MLA KV state persistent across generated tokens.
- Overlap I/O with GPU work without allowing a mapping or buffer to disappear
  before its last Metal command has completed.

K3 is selected by passing its SafeTensors directory or GGUF file to
`ds4_engine_open`.
`ds4`, `ds4-agent`, `ds4-server`, `ds4-bench`, and `ds4-eval` all use that same
backend. Immutable model weights, resident buffers, streaming banks, and the
execution workspace are shared; each session owns independent KDA/MLA state
and route history. Execution is serialized inside the backend because the
large transient workspace is shared. The tokenizer adapter renders official
XTML, including preserved reasoning, native tool declarations/calls/results,
and `<|end_of_msg|>` turn boundaries. Session payloads store token history and
replay layer-major prefill on restore rather than inventing a second K3 KV
format.

Contiguous-layer distributed inference is supported for the two-node resident
GGUF deployment. Vision, CUDA, ROCm, MTP/DSpark, steering, and reduced power
remain outside the current scope.
Non-Metal builds link only the lightweight K3 file detector, allowing every
shared binary to reject a K3 directory or GGUF with a clear backend error
without linking the ICU tokenizer or falling through to the legacy GGUF
loader.

The integrated `ds4` CLI has also completed a bounded end-to-end GGUF pass
through all 93 layers and the output head using the sparse in-progress
artifact. It processed the normal 38-token XTML rendering of a one-character
prompt without mapping the full file. This is a control-flow and resource
lifetime test only: tensors after the converter journal frontier were still
sparse zeros, so its sampled output is not a quality result. The tokenizer-only
`--dump-tokens` path detects K3 before the generic GGUF loader and works for
both the SafeTensors directory and K3 GGUF.

## 2. Model facts that drive the design

The checkpoint has:

| Property | Value |
|---|---:|
| Transformer layers | 93 |
| Hidden width | 7,168 |
| Vocabulary | 163,840 |
| Attention heads | 96 |
| Head width | 128 |
| Context limit | 1,048,576 |
| KDA layers | 69 |
| Gated MLA layers | 24 |
| Routed experts per MoE layer | 896 |
| Selected routed experts | 16 |
| Shared experts | 2 |
| Routed latent width | 3,584 |
| Routed expert intermediate width | 3,072 |
| Shared expert intermediate width | 6,144 |

Layer 0 has KDA attention and a dense feed-forward network. Layers 1 through
92 use Stable LatentMoE. Gated MLA appears every fourth layer and at the last
layer; the remaining attention layers use KDA.

The official index currently gives each transformer layer its own shard:
zero-based layer `L` is in `model-(L + 1)-of-00096.safetensors`. Global text
tensors are in shard 94. Shards 95 and 96 contain the projector and vision
tower and are not needed by the text runtime. This physical layout is already
well suited to direct layer-major streaming.

The full checkpoint is about 1.56 TB. A layer descriptor must therefore be a
small mapping and tensor table, not an eager allocation containing an entire
layer.

## 3. Required execution schedule

### 3.1 Prefill

Prefill processes a bounded row block through all 93 layers:

```text
map/prepare layer 0
for L in 0..92:
    wait only if layer L is not ready
    start static read-ahead for layer L + 1
    execute attention and routing for layer L
    once routing is known, read selected experts for layer L
    execute routed and shared experts
    release or demote pages that are outside the cache policy
```

For a large prompt block, the union of selected experts approaches all 896
experts. At that point one sequential read through the layer shard is likely
better than hundreds of small range reads. The runtime needs both policies:

- **Selective mode:** prefetch only the expert spans selected by the rows in
  the current block.
- **Sequential mode:** read the complete layer shard in file order.

The crossover must be measured. A row-count threshold is only an initial
heuristic because expert concentration, filesystem cache state, queue depth,
and SSD range-read behavior matter more than row count alone.

### 3.2 Generation

Generation remains layer-major even though there is only one new row:

```text
start static read-ahead for layer 0
for L in 0..92:
    wait for layer L static ranges
    start static read-ahead for layer L + 1
    execute attention and router for layer L
    read the exact 16 selected experts for layer L
    execute routed experts, shared experts, and residual updates
start output-head read-ahead before the last layer finishes
compute logits and sample
```

The static ranges of `L + 1` are known in advance. Its routed experts are not:
the exact expert IDs are only known after the next layer's router has consumed
the current layer's output. The baseline must not predict them. It should
instead overlap:

- next-layer static I/O with current-layer GPU work;
- current-layer selected-expert I/O with independent current-layer shared and
  latent projection work;
- output-head I/O with the final layer's expert work.

Every generated token repeats this same layer traversal. Tensor descriptors and
file mappings remain open across tokens so generation never reparses 93
SafeTensors headers or recreates mappings in its hot path.

## 4. Exact decode byte model

This section estimates storage traffic for one generated token when pages are
cold. Decimal GB is used for SSD rates; GiB is shown where useful.

### 4.1 One routed expert

For one expert:

| Tensor | Bytes |
|---|---:|
| `w1` MXFP4 payload, `3072 x (3584 / 2)` | 5,505,024 |
| `w1` E8M0 scales, `3072 x (3584 / 32)` | 344,064 |
| `w3` MXFP4 payload | 5,505,024 |
| `w3` E8M0 scales | 344,064 |
| `w2` MXFP4 payload, `3584 x (3072 / 2)` | 5,505,024 |
| `w2` E8M0 scales, `3584 x (3072 / 32)` | 344,064 |
| **Total per expert** | **17,547,264** |

That is 16.735 MiB per expert. Sixteen unique selected experts require
280,756,224 bytes, or 267.75 MiB, per MoE layer and generated token.

### 4.2 Non-routed MoE weights

The weights used regardless of routing are:

| Component | Bytes |
|---|---:|
| Router weight and correction bias | 12,848,640 |
| Latent down and up projections | 102,760,448 |
| Latent RMS norm | 7,168 |
| Three shared-expert matrices | 264,241,152 |
| **MoE static total** | **379,857,408** |

### 4.3 Attention and complete layer traffic

A KDA attention block plus its AttnRes vectors is 887,886,848 bytes. Adding
the static MoE weights gives 1,267,744,256 bytes of static data in a KDA MoE
layer.

A gated MLA attention block plus its AttnRes vectors is 464,478,208 bytes.
Adding the static MoE weights gives 844,335,616 bytes of static data in an MLA
MoE layer.

Layer 0 has 887,886,848 bytes of KDA/AttnRes data and three BF16
`33792 x 7168` dense matrices. Its total is 2,341,213,184 bytes.

For a generated token that selects 16 distinct experts:

| Layer kind | Static + selected experts | GiB | I/O at 6 GB/s |
|---|---:|---:|---:|
| Layer 0 | 2,341,213,184 B | 2.180 | 390 ms |
| KDA MoE | 1,548,500,480 B | 1.442 | 258 ms |
| MLA MoE | 1,125,091,840 B | 1.048 | 188 ms |

Across the whole model:

| Recurring data | Bytes | GiB |
|---|---:|---:|
| All layer-static weights | 108,811,877,376 | 101.339 |
| 16 experts in each of 92 MoE layers | 25,829,572,608 | 24.056 |
| BF16 output head | 2,348,810,240 | 2.188 |
| **Cold decode total** | **136,990,260,224** | **127.582** |

This excludes small activation/state traffic and assumes that each selected
expert is unique within its layer. It also excludes filesystem and range-read
overhead, so the following table is an optimistic storage lower bound, not a
performance promise:

| Sustained SSD bandwidth | Minimum cold seconds/token | Maximum cold tokens/s |
|---:|---:|---:|
| 4 GB/s | 34.25 | 0.029 |
| 6 GB/s | 22.83 | 0.044 |
| 8 GB/s | 17.12 | 0.058 |
| 10 GB/s | 13.70 | 0.073 |

### 4.4 Can current-layer compute hide next-layer loading?

For cold pages, no.

At 6 GB/s, loading the next layer takes about 188 ms for MLA or 258 ms for
KDA. By comparison, a simple weight-bandwidth floor at 300 GB/s of effective
GPU memory bandwidth is:

- KDA static weights: `1.268 GB / 300 GB/s = 4.2 ms`;
- MLA static weights: `0.844 GB / 300 GB/s = 2.8 ms`;
- 16 MXFP4 experts: `0.281 GB / 300 GB/s = 0.94 ms`.

Kernel launch costs, attention state work, activation quantization, and
imperfect bandwidth raise the real GPU time. They do not plausibly turn a
single layer into 188-258 ms of useful GPU work. Even a measured 20 ms layer
would hide only 8-11% of the cold next-layer read at 6 GB/s.

The overlap condition for layer `L` is:

```text
GPU_time(L) >= storage_time(static(L + 1))
```

and, after routing:

```text
independent_GPU_time(L) >= storage_time(selected_experts(L))
```

Both must be measured separately. A single total-token timer cannot explain
whether the loader, router readback, page faults, or Metal work is stalling.

This result does not invalidate layer-major streaming. It means that overlap
alone cannot solve cold generation. Layer-major is still the correct baseline
because it hides all I/O that is hideable, has bounded live state, follows the
checkpoint's physical layout, and gives the cache the most predictable access
order.

### 4.5 The cache changes the generation result

The 108.8 GB decimal layer-static set is 101.3 GiB. It is close enough to the
capacity of a 128 GiB unified-memory machine that much of it may remain resident
after warmup, but the OS, Metal allocations, recurrent/KV state, scratch,
activations, output head, and expert pages all compete for the remainder.

If every static page remained resident and only selected expert pages plus the
output head came from SSD, traffic would be 28.18 GB per token:

| Sustained SSD bandwidth | Seconds/token | Tokens/s |
|---:|---:|---:|
| 4 GB/s | 7.04 | 0.142 |
| 6 GB/s | 4.70 | 0.213 |
| 8 GB/s | 3.52 | 0.284 |
| 10 GB/s | 2.82 | 0.355 |

That is a warm-cache lower bound. A 128 GiB system is unlikely to retain all
static weights while also retaining a useful expert cache, so real generation
should fall between the 28.18 GB warm floor and the 136.99 GB cold case.
Measured page residency and bytes read are therefore required; nominal model
size is not enough.

## 5. Prefill math

One MoE layer contains 896 routed experts totaling:

```text
896 * 17,547,264 = 15,722,348,544 bytes
```

If routing were uniform and each row selected 16 experts independently, the
expected number of unique experts for `T` rows would be:

```text
E[unique(T)] = 896 * (1 - (1 - 16 / 896)^T)
```

| Rows | Expected unique experts | Expert bytes |
|---:|---:|---:|
| 1 | 16.00 | 0.281 GB |
| 8 | 120.28 | 2.111 GB |
| 16 | 224.41 | 3.938 GB |
| 32 | 392.62 | 6.889 GB |
| 64 | 613.20 | 10.760 GB |
| 128 | 806.74 | 14.156 GB |
| 256 | 887.11 | 15.566 GB |

Real K3 routing is not uniform; stable experts may be much hotter. The table is
a neutral starting point for choosing selective versus full-layer read-ahead.
By 128 rows, random routing touches about 90% of experts, so a sequential layer
read should usually win. At 64 rows, selective traffic is lower on paper, but a
full sequential read may still be faster than hundreds of range reads.

Unlike generation, prefill GPU work scales with the number of rows while a full
layer read is fixed. There will be a prompt-block size above which matrix
multiply time can hide most or all next-layer I/O. It must be found by sweeping
row count and recording both GPU and loader timelines. The initial threshold of
64 rows is a benchmark hypothesis, not an architectural constant.

## 6. Phase A: correct direct loader

The loader must establish correctness before optimizing residency:

1. Parse the SafeTensors header with bounds and overflow checks.
2. Validate every required tensor name, dtype, shape, and byte span.
3. Map shards read-only and expose tensor views without copying.
4. Build all 93 layer descriptors once at model open.
5. Bind global tensors from shard 94 and ignore vision-only shards.
6. Keep mappings alive until every Metal no-copy view using them has completed.
7. Produce clear errors for a missing, partial, mismatched, or unsupported
   checkpoint.

The index is the source of truth. The `layer -> shard` shortcut can be used only
after validating that the downloaded index has the expected mapping.

## 7. Phase B: numerically faithful Metal path

Implement and test the architecture in small independent pieces:

1. BF16/F32 tensor views, RMS normalization, residual interpolation, and dense
   projections.
2. KDA convolution, bounded decay, recurrent state update, query
   normalization, and output projection.
3. Gated MLA query/latent-KV projections, positional treatment, cache update,
   attention, gate, and output projection.
4. Stable LatentMoE router: sigmoid scores, correction bias for top-16
   selection, uncorrected score gathering, and normalization.
5. Latent down projection and normalization.
6. MXFP8 activation quantization with E8M0 block scales.
7. MXFP4/MXFP8 expert matrix multiplication with the checkpoint's nibble and
   scale ordering.
8. Exact SiTU activation and second activation quantization.
9. Routed-expert weighted accumulation, shared experts, latent up projection,
   and residual update.
10. Final normalization, output head, top-p sampling, and tokenizer/chat
    template behavior.

Decode should quantize the routed latent once per layer and reuse it across all
16 selected experts. Expert output accumulation should avoid materializing 16
full hidden-width outputs when a fused or bounded partial reduction is
possible.

## 8. Phase C: layer-major I/O baseline

Use one persistent loader state and a bounded number of mappings:

- The main execution thread owns model state and Metal command ordering.
- A next-layer worker prepares known static ranges for `L + 1`.
- A bounded expert worker pool prefetches the six payload/scale spans for each
  selected current-layer expert.
- A loader result contains the layer number and generation epoch so stale work
  cannot be consumed after cancellation.
- The current layer starts only after joining its own prerequisite I/O.
- Immediately after that join, the main thread submits the next layer's known
  static read-ahead.
- Selected expert prefetch starts as soon as router results are available.
- The output head starts loading before final-layer expert execution.

For macOS, compare `mmap` page faults, explicit range reads, and advisory
read-ahead using the exact K3 access pattern. Do not assume that an advisory API
has completed I/O merely because its call returned.

The first baseline must follow the same residency discipline as the existing
Metal SSD-streaming path:

- map layer ranges as no-copy Metal views and release those views after the
  layer command buffer completes;
- use `F_RDADVISE` for known next-layer static ranges;
- advise selected expert ranges only after routing;
- never CPU-touch every page of a layer, selected expert set, or output head
  merely to force prefetch completion;
- keep explicit `pread` expert data only in a byte-budgeted cache.

CPU page touching is a diagnostic mode only. Across one cold decode token it
can force the 101.3 GiB static set, 24.1 GiB selected-expert set, and 2.2 GiB
output head resident in one process, leaving no safe headroom on a 128 GiB
machine.

Start with modest concurrency. Six ranges for each of 16 experts can otherwise
turn one token into 96 competing requests per layer. Sweep worker counts
`1, 2, 4, 8` and measure total time, tail latency, CPU time, and SSD throughput.

## 9. Instrumentation required to find the real floor

Add a low-overhead trace record for every layer and token:

| Field | Purpose |
|---|---|
| layer kind and row count | Separate KDA, MLA, and prefill regimes |
| current-layer join wait | Direct measure of unhidden next-layer I/O |
| static read start/end and bytes | Measure actual next-layer work |
| attention/router GPU start/end | Locate the routing dependency |
| route readback duration | Detect CPU/GPU synchronization cost |
| selected expert IDs and union size | Explain expert traffic |
| expert read start/end and bytes | Measure post-routing stall |
| shared/latent GPU interval | Measure expert I/O overlap window |
| command encode/commit/complete | Separate CPU submission from GPU work |
| page faults and process I/O bytes | Distinguish cache hits from disk reads |
| output-head read and compute | Keep the final projection visible |

Produce both a per-layer trace and a one-line token summary:

```text
token, rows, cold/warm, gpu_ms, static_io_ms, expert_io_ms,
join_wait_ms, bytes_read, cache_hits, token_ms
```

Measurements must include:

- cold runs after intentionally dropping only the pages the test owns;
- warm runs without artificial cache manipulation;
- repeated deterministic prompts;
- short and long prefills;
- early and long-context generation;
- SSD concurrency sweeps;
- selective/full-layer crossover sweeps;
- at least p50 and p95 token latency, not only average throughput.

## 10. Definition of the layer-major floor

No alternative execution order should be attempted until all of these are
true:

1. SafeTensors headers and layer descriptors are absent from the per-token hot
   path.
2. No layer mapping or Metal view is recreated unnecessarily.
3. The next known static read starts immediately after the current-layer join.
4. Current selected experts start prefetching immediately after routing.
5. Static and expert I/O concurrency has been swept rather than guessed.
6. Selective and sequential prefill thresholds have been swept over real
   prompts.
7. Cold and warm traces report actual storage bytes and cache residency.
8. GPU time, I/O time, and join waits are available for every layer kind.
9. The same-access-pattern SSD microbenchmark agrees with runtime I/O
   within a defensible margin.
10. Correctness tests and deterministic output remain unchanged throughout
    tuning.
11. Observed token time is within 10-15% of the applicable lower bound:

```text
max(critical_GPU_time, critical_storage_time)
```

The lower bound must use measured critical-path bytes and overlap windows, not
the checkpoint's total size. If the remaining gap is larger, the trace must
explain it before the design is declared exhausted.

## 11. Optimizations that remain layer-major

These are allowed before declaring the baseline exhausted because they improve
the same execution schedule:

### 11.1 Cache-aware residency

Separate static and routed pages in accounting. Prefer retaining static pages
because all 108.8 GB recur every token. Use a bounded per-layer expert cache
keyed by `(layer, expert)` for the remaining capacity. Track real hits and
evictions rather than relying on page-touch intent.

The policy should account for memory pressure explicitly. A larger expert cache
that causes static pages to churn can be slower than a smaller one.

### 11.2 Static and expert I/O lanes

Give next-layer static reads predictable progress while current-layer expert
ranges are fetched. Compare:

- one ordered queue;
- one static queue plus a bounded expert pool;
- a single explicit-I/O scheduler with priorities and byte budgets.

The winning policy is the one with the smallest current-layer join wait and
expert stall, not the highest aggregate benchmark bandwidth.

### 11.3 Batched range construction

Merge adjacent selected expert spans when the resulting extra bytes cost less
than separate I/O setup and page faults. Keep payload and scale layout exact.
Record useful versus speculative bytes so range coalescing cannot appear free.

### 11.4 Prefill block sizing

Tune row-block size jointly with:

- unique experts selected;
- sequential-read crossover;
- activation/scratch memory;
- GPU occupancy;
- time available to hide the next layer.

Avoid a block size that raises memory pressure enough to evict the next layer
before it is used.

### 11.5 Command scheduling

Encode independent shared/latent work so it can execute while selected expert
pages arrive. Use Metal events only where a real data dependency exists.
Measure command-buffer count and CPU submission cost before adding fusion.

## 12. Alternatives only after the floor

The following ideas are deliberately deferred until Section 10 is satisfied.

### 12.1 Speculative next-layer expert prefetch

Predict likely experts in layer `L + 1` from recent tokens or neighboring
layers, then prefetch them while `L` executes. Routing remains exact; a miss
falls back to the normal post-router fetch.

This is useful only if measured prediction hit rate saves more bytes and time
than false-positive reads consume. Report precision, recall, useful bytes,
speculative bytes, and latency. It must never become a routing approximation.

### 12.2 Optional sidecar layout

An optional local cache could store static ranges contiguously and arrange
expert payload/scale spans for fewer reads. The original SafeTensors files
remain authoritative and the sidecar is validated by checkpoint revision and
tensor metadata.

This may improve queueing and range overhead, but it sacrifices the simplicity
of direct checkpoint access and needs about another model's worth of storage if
applied broadly. It is not justified before direct SafeTensors measurements
show range setup or shard layout to be a dominant residual cost.

### 12.3 Larger resident layer windows

Keep two or more prepared layers when memory permits. This can smooth I/O
jitter but does not reduce recurring bytes. It is useful only if traces show
short bursts or tail latency, rather than total storage bandwidth, causing
stalls.

### 12.4 Cross-device storage or compute

Stripe shards across multiple independent SSDs, or split layers/experts across
machines. This can raise aggregate bandwidth and capacity but introduces
coordination and communication. It should use the single-machine trace as its
cost model instead of starting as an architecture experiment.

### 12.5 Multi-request layer batching

For several concurrent sequences, execute the same layer for a batch of
requests before advancing. This amortizes static weight reads across requests
and may substantially improve aggregate tokens/s. It increases per-request
latency and requires a scheduler, but remains layer-major at the batch level.

### 12.6 Different model traversal

Expert-major or broad token-major traversal is last. For one autoregressive
sequence, token `T + 1` cannot be routed until token `T` has reached the output
head and been sampled, so there is little useful token-level lookahead without
speculation. Any traversal change must identify a concrete dependency it
removes and compare against the measured layer-major floor.

## 13. Correctness and performance validation

### 13.1 Unit tests

- SafeTensors header parsing, integer overflow, malformed offsets, shape/dtype
  rejection, and tensor lookup.
- Exact MXFP4 nibble order and E8M0 scale interpretation.
- MXFP8 activation encoding, saturation, zero, subnormal, infinity, and NaN
  policy against the official implementation.
- Router top-16 selection, correction bias, score gathering, and
  normalization.
- SiTU values over representative and extreme inputs.
- KDA one-step and multi-step state updates.
- MLA cache append and attention at multiple positions.
- Tokenizer encode/decode and chat-template fixtures.

### 13.2 Reference comparisons

For small tensors and short sequences, compare intermediate values with the
official Transformers/vLLM implementation:

- embeddings and first normalization;
- KDA and MLA attention output;
- router selected IDs and weights;
- latent projection;
- each expert projection before and after activation quantization;
- shared and routed MoE outputs;
- final logits.

Use layer-specific tolerances justified by BF16 and MXFP8 arithmetic. Expert
IDs should match exactly unless a documented score tie exists.

### 13.3 End-to-end tests

1. Load every text tensor from the fully downloaded checkpoint.
2. Run a one-token raw prompt through all 93 layers.
3. Run multi-token prefill through both selective and sequential policies.
4. Confirm that two-token batched prefill and sequential one-token state
   updates agree within tolerance.
5. Generate deterministic greedy tokens from raw and chat prompts.
6. Run top-p sampling with the model-card defaults.
7. Exercise context growth across KDA state and MLA cache boundaries.
8. Repeat under AddressSanitizer/UndefinedBehaviorSanitizer where Metal is not
   required, and run strict warning builds plus the Clang static analyzer.

### 13.4 Performance reports

Report at least:

- hardware, RAM, macOS version, free disk, and checkpoint revision;
- prefill tokens/s by row block;
- generation seconds/token and tokens/s;
- cold and warm actual bytes read per token;
- static and selected-expert cache hit rates;
- per-layer GPU time and join wait for KDA and MLA;
- SSD worker count and selective/full threshold;
- peak resident memory and memory-pressure state;
- output correctness mode and sampling parameters.

The first useful result is not a headline tokens/s number. It is a trace that
shows which portion of each layer's storage time is hidden and whether the
remaining limit is SSD bandwidth, cache churn, routing dependency, Metal
execution, or CPU submission.

## 14. Completion gates

The direct K3 runtime is complete for its initial scope when:

- the pinned official text checkpoint loads without conversion;
- all required tensors are shape/dtype validated;
- prefill and generation both use the measured layer-major schedule;
- MXFP4 weights and MXFP8 activation behavior match the references;
- deterministic full-model generation succeeds;
- cold and warm I/O traces explain observed performance;
- no correctness regression appears when I/O overlap is disabled;
- the README documents supported hardware, command-line use, memory/storage
  expectations, and known limitations;
- alternative streaming schedules remain deferred unless the layer-major floor
  criteria have actually been met.
